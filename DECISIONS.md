# Decisions and assumptions

Each entry: requirement ID, the decision, and why. The brief (`BRIEF.md`) wins over anything here; these only fill gaps or resolve tensions within it (2.2.b, 2.3.e).

## Process

- **D1 (13.3, user hook).** The user's global push hook tags `v1.0.0` on a repo's first push, which 13.3 forbids. With the user's approval (2026-10-29) a one-off annotated baseline tag `v0.1.0` was pushed with the first commit. The hook only bumps the minor version, so every later push is `v0.N.0` and `v1.0.0` is never created automatically. Push with a plain `git push`: the hook reads the first word after `push` as the remote name, so `git push -u ...` silently produces no tag.
- **D2 (2.12, Learning output style).** The session's output style asks for human-written code contributions. The brief requires unattended work (2.1, 2.3.e), so no "Learn by Doing" pauses are used for this project. Explanations are still given in chat.
- **D3 (11.1, 3.6).** `check.ps1` targets PowerShell 7 (`pwsh`), installed 2026-10-29 (7.6.9).
- **D4 (11.4, disk).** Model, llama.cpp and corpus downloads go to `%LOCALAPPDATA%\GlobalAutocorrect\cache`. Only 12.5 GB was free at planning time, so Spike A was going to keep at most two GGUFs at once. Free space later rose to 56 GB, so all three Q5_K_M candidates are kept until the spike decides.
- **D20 (2.8, Spike B and E2E).** Windows Sandbox can't run Word or Outlook, and Spike B needs both, so the screen-driving tests run on the real desktop. They wait until there has been no keyboard or mouse input for 2 minutes. A low-level hook watches for non-injected input during each run; if any arrives, that target stops and is retried at the next idle period. The tests only ever close windows they opened. For Edge they use a separate temporary profile, so the user's own browser windows are never touched.

## Text access and timing

- **D5 (4.2).** "Only the user's own typing" is enforced by a *typed buffer*: the characters produced by physical keystrokes since the last break, translated with `ToUnicodeEx` on the UK layout. A correction may only touch characters inside the typed buffer, and only if the field's text before the caret still ends with that buffer. Any mismatch (paste, dictation, text expander, host-app autocorrect, click elsewhere) is a session break. Injected events that are not ours (`LLKHF_INJECTED` without our tag) and physical Ctrl+V / Shift+Insert are also breaks.
- **D6 (4.6.c, 4.3.a).** Writes are key-relative: a batch moves Left from the caret, deletes, types and moves back. Windows guarantees a `SendInput` batch is not interleaved with user input, and anything typed after the batch is queued behind it. So the hazard is only keys that arrive between our snapshot and our `SendInput` call. That is checked with a key sequence number from the hook, just before sending.
  - AI writes: also wait for a 150 ms keystroke gap (4.6.c) and require the snapshot text to be a prefix of the current text before the caret, with any extra characters coming from keystrokes recorded since the snapshot. Strict "text unchanged" would discard almost every AI fix for someone who keeps typing, which defeats 0.2. The edit position is rebased by the appended length.
  - Instant writes (4.3): the decision is made within 100 ms of the word-ending key. If no key has arrived since that key, the write goes out at once. Otherwise it is retried at the next 150 ms gap, using the same key-relative offsets.
- **D7 (4.6.a).** "Never touch the word being typed or the word before it" applies to the AI layer. The instant layer's job (4.3.a) is to fix the word just finished, so it is the explicit exception. It still never touches the word currently being typed.
- **D8 (10.7.a).** Edits never cross a line break. The AI context (4.4.b) is taken from the current paragraph only, because caret movement over line breaks differs between editors (CRLF vs LF, soft wraps). Left/Right counts use text elements (grapheme clusters), not UTF-16 units.
- **D9 (4.8.b).** "Reverts the most recent correction from anywhere" means anywhere in the field that holds the correction, wherever the caret is. If a different field or window has focus, the shortcut does nothing and the tray shows a short notice. The app never moves focus by itself.
- **D10 (4.8, 14.5).** Only the single most recent correction is held in memory, for undo. Nothing is written to disk, and there is no list.
- **D11 (10.6, 10.3.b).** UI Automation uses raw COM (`Interop.UIAutomationClient`) on a dedicated STA thread with `IUIAutomation2` connection and transaction timeouts of 250 ms. If a call hangs past 500 ms, the thread is abandoned and replaced, and that window is skipped for 30 s.

## Model and data

- **D12 (5.3, 2.3.d).** llama.cpp is pinned to build `b11960`, the build that the stable `v0.8.0` release points to, not the newest nightly. GGUFs come from `unsloth/*-GGUF`, pinned by repository commit: they're the most downloaded, smallest at each quantisation, and Apache-2.0.
- **D13 (5.4, 12.8).** Thinking is disabled two ways: the `--reasoning-budget 0` server flag, and `chat_template_kwargs: {enable_thinking: false}` in each request.
- **D14 (7.2, 1.5).** Corpus: Leipzig Corpora Collection `eng-uk_web-public_2018_1M` (UK web text, CC BY). It provides both the SymSpell word frequencies and the prediction n-grams. Every word is filtered through Hunspell en_GB-ise, so American spellings never appear as suggestions or correction targets (3.4).
- **D15 (7.3).** The user's typing history is stored as unigram word counts only. Pair counts could partly reconstruct sentences, so they are not kept.
- **D16 (3.4, 4.5).** Mechanism for "never Americanise": an AI substitution is rejected if the new word is not valid in Hunspell en_GB-ise or the personal dictionary, unless it is a capitalised proper noun at least as similar as 4.5.a requires. This is a rule on the mechanism, not a word list (2.10).
- **D17 (6.1).** Each eval message is short (one to three sentences), so a message fits the AI context window of 4.4.b. Split: 450 messages (400 synthetic-noise plus 50 hand-garbled) into 250 tuning and 200 holdout, by a fixed seeded shuffle.
- **D19 (4.5.d, 6.1.c, 6.4).** For the "more than 50% of words would change" guard, a word changes when its spelling changes, compared ignoring case and apostrophes: substitutions, insertions and deletions. Capitalisation, apostrophe, punctuation and spacing fixes are always acceptable under 4.5.a and don't count. Counting them would reject almost every lower-case, unpunctuated quick message, which works against 0.2 and 6.4. The ratio is measured on the AI context after the instant layer has already fixed the obvious typos (4.3).
- **D21 (3.3, 8.6, 10.5).** llama-server's default is "no API key, CORS allows all origins". Any web page open in the user's browser could then call it on 127.0.0.1, and the `/slots` endpoint can show the last prompt, which is typed text. The host therefore starts llama-server with a random per-launch `--api-key`, sends it as a Bearer header, and passes `--no-slots`. `/health` stays unauthenticated for the watchdog. `-lv 4` is used so the log shows `using device CUDA0` and `offloaded N/N layers to GPU` for the verify script (5.8.a).
- **D22 (10.7.a, Spike B).** Replacement text is typed as real virtual-key presses on the foreground window's layout (`VkKeyScanEx`, Shift added as needed, inverted for letters when Caps Lock is on), in the same single tagged batch. `KEYEVENTF_UNICODE` packets are used only for characters with no key on the layout. Spike B run 1 showed Win11 Notepad turning a burst of Unicode packets into the last character, typed after the Right-arrows (`alpha bravo  delta echoeeeeeee`). Real key events keep their order in every app.
- **D23 (4.3.c, 4.3.d, 2.10).** In the instant layer, distance-1 candidates are ranked by a noisy-channel score: corpus frequency × how likely that one slip is on a UK keyboard (doubled key 0.05, adjacent swap 0.04, missed double 0.04, neighbouring key 0.03, extra neighbouring key 0.02, other insert/delete 0.01, other substitution 0.003). The top candidate must beat the next by 4×. 4.3.c's conditions stay necessary. This only adds caution where two corrections are about equally likely: `ofr` could be "of" or "for", so the AI decides. `bookk` → `book` (doubled key) stays instant, as 0.2.a requires. Distance 2 uses 4.3.c's 10× frequency rule unchanged. A word that splits into two valid words (`ifyou`) is a missing space, so it is left for the AI rather than "corrected" by deleting letters.
- **D24 (4.4.c, 4.4.d).** The model's reply is trimmed and usually ends with a full stop. Before diffing, the user's own leading and trailing whitespace is put back, and closing punctuation is removed if the user hadn't ended the sentence. Without this the space just typed was deleted (`policy.Please`), and a full stop was added to sentences still being typed.
- **D25 (4.4.d, 4.5.a).** A capitalisation change is accepted at a sentence start, for a stray capital mid-sentence (`On` → `on`), or when the typed form isn't a word on its own (`london`, `monday`, `i`). Capitalising an ordinary word mid-sentence (`senior analyst` → `Senior Analyst`) is a style change and is rejected.
- **D26 (4.5.a).** When the model splits or merges words, the letters must be within edit distance 1 of what was typed. Normalised distance over a long run-together word would otherwise hide a word swap (`stationfor` → `station at`).
- **D27 (4.4.c, 4.5.a, 4.3.d).** Three tuning-set findings. (1) The diff aligner also handles three words run together, or one word split across two spaces (`meknowif` ↔ `me know if`); without that the parts were judged separately and gave `meknowif if`. (2) One edit that is a likely UK-keyboard slip (neighbouring key, doubled key, adjacent swap) is accepted even when it fails the normalised-distance threshold, because every substitution in a one- or two-letter word scores high (`q` → `a`). It's a setting (`AcceptLikelyKeyboardSlips`), on by default and off under "Cautious". (3) The instant layer leaves a word alone when the previous word plus this one is a valid word (`s andwich`), because that's a misplaced space for the AI.
- **D28 (10.7.a).** When the text between an edit and the caret is a short run (up to 3) of spaces and punctuation, usually just the key that finished the word, the batch deletes it with the word and types it again instead of stepping over it with Left and Right. E2E in Edge showed the arrow keys applied out of step with a key typed straight after the batch (`thed og`). Longer tails, which contain words, are still stepped over, so a word after the edit is never typed again. 10.7.a's "one SendInput batch relative to the caret" is unchanged.
- **D29 (4.8.a, 4.8.b).** Undo is always asked for while a modifier is still down (the Ctrl of Ctrl+Z, or the shortcut's Ctrl+Alt). The engine loop holds the undo until the keyboard hook has seen those keys released, for at most 1 s; after that the writer's release-and-restore of held modifiers takes over. Windows' own key state lags behind back-to-back events, so the hook's view is used. E2E found an undo in a WPF box that removed the correction and then lost the retyped word: the letters had arrived as Ctrl+T, Ctrl+E, Ctrl+H.
- **D30 (4.5.a, 4.5.e, 4.4.d).** Accuracy push after RC1, tuning set only. (1) Two likely keyboard slips are accepted as a typo however short the word: the best route through one intermediate spelling must score at least "a random slip with a neighbouring key" (`by` → `but`: missed t, then y for u; `to` → `got`; `hteoosition` → `the position`). Two random edits still fail (`it` → `on`), the new words must still be valid, and "Cautious" turns it off with D27. (2) A lone `i` (and `i'm`, `i'll`) is always capitalised: the dictionary lists "i" as a letter, so D25's "isn't a word on its own" test missed it. Tuning set 90.8% → 92.7%, false edits unchanged at 0.20%. A second clean-up pass was also measured (90.5%, twice the latency) and not adopted.
- **D31 (4.5.a, 4.5.b, 4.4.d, 5.4).** More tuning-set findings where the model was right and a rule threw the fix away. (1) A spelling fix and a dropped function word beside it can be aligned as one edit (`si` → `is the`). The fix is judged on its own and the function word as 4.5.b allows, but only if what remains is a real spelling fix of about the same length: `stationfor` → `station at` (D26) and `Spare room` → `The spare room` (an added article plus a lost capital) are still rejected. (2) A capital after a sentence end that the same reply adds (`afternoon something` → `afternoon? Something`) counts as a sentence start. (3) A possessive or "is" contraction of a valid word (`heating's`) counts as a word. (4) Prompt v4: dropped small words are put back "where any native writer would clearly use" them, with two more dropped-"the" examples, one heavy-typo example and one more clean example (none from the eval data, 6.1.e). Not changed: `it` → `IT`, which would be wrong far more often than right.
- **D32 (1.4, 5.3.a, 2.4.c).** The 8-bit file of the chosen model (`gemma-4-E4B-it-Q8_0.gguf`, same pinned revision) was measured on the tuning set at the user's request: 94.4% errors fixed and 0.20% false edits, exactly the same as the 5-bit file, with 3 fixes gained and 3 lost. It was slower (p50 420 ms against 371 ms) and needed about 5.4 GB of the 8 GB of graphics memory against about 3.5 GB, which leaves less room for other apps (README "Known limits"). The 5-bit file stays the default and the manifest is unchanged. The remaining misses are the model's own limits, not rounding in its weights.
- **D33 (1.4, 5.5, 6.4).** The user lifted rule 1.4 to consider a bigger model, then chose speed: nothing about twice as slow. The models that fit 8 GB (Qwen 3.5 9B, 5.3 GB, and Gemma 4 12B, 6.6 GB) were estimated at roughly 0.6–0.9 s per clean-up against 0.36 s now, so neither was downloaded or measured. Gemma 4 E4B stays the default, and 92.9% against the 95% target is accepted as the trade-off for speed (README "Known limits").
- **D34 (4.8.a, 4.8.b, 4.8.c, 9.4).** At the user's request the app no longer takes Ctrl+Z (4.8.a is withdrawn): intercepting it straight after a correction would clash with too many other apps' own undo. Ctrl+Z now always reaches the app. Undoing a correction is the shortcut only (Ctrl+Alt+Z, configurable, 4.8.b), which still adds the word to the personal dictionary (4.8.c) and still waits for the shortcut's keys to be released (D29). The hook's undo arm and its swallowed key are gone; the first-run window no longer shows Ctrl+Z. The engine keeps its "local" undo path for tests only. E2E: `R4_8_b_TheUndoShortcutRevertsTheCorrection_R4_8_c` and `R4_8_a_CtrlZIsLeftToTheApp_D34`.
- **D35 (1.10, 14.7, 13.1, 13.3).** The brief says "no CI service", but the user asked (2026-10-30) for a GitHub Actions release as well, so `.github/workflows/release.yml` builds the zip on a GitHub-hosted `windows-latest` runner and attaches it to a GitHub Release. Building and testing still happen on the laptop first (`check.ps1`, `deploy.ps1`); the workflow only repeats the fast tier's unit tests (Core, Llm, Windows, App), never Model or E2E, which need the GPU, the model cache and the keyboard. It doesn't run the eval either: `artifacts/metrics.json` is the newest committed `docs/metrics/holdout-*.json`, so a CI zip ships the same measured accuracy as a local one (6.6). It runs by hand (`gh workflow run release.yml`) or on a pushed tag matching `v*-rc*`. The push hook's tags are plain `v0.N.0` and never match, so an ordinary push never publishes anything (D1). The release tag is `v` plus the app's `<Version>` (`v0.9.0-rc1`); the hook ignores tags with a suffix, so it doesn't disturb the hook's numbering. A version without a suffix fails unless the run is started with `final` ticked, which is only for after the user confirms the app on their PC (13.3), and the workflow refuses to reuse a tag that points at another commit.
- **D36 (4.5.a, 4.5.d, 4.5.e).** User report: in a long, badly typed paragraph, obvious misspellings were left in place. A new stress set (`data/eval/stress.jsonl`: 16 new multi-sentence messages at heavy and "severe" noise, each also clean, plus the user's own paragraph) showed why. (1) 4.5.d rejected the whole correction when more than half the words changed, which in a garbled paragraph is the correct fix. (2) "Too dissimilar" refused fixes of words that aren't words (`gorecastsays` → `the forecast says`, `iveer` → `the river`, a stray `t` → `the`). A word that isn't a word can't be the user's wording, so for a lower-case non-word (or a stray single letter other than a/I) the fix doesn't count towards 4.5.d, and is accepted at up to 0.65 apart when the first letter is kept, with small words added at either end. Real words, capitalised words (names) and the D26 split guard keep the strict rules; "Cautious" turns it off. Stress set 83.5% → 89.2%; tuning set unchanged.
- **D37 (4.5.a, 4.4.d).** User report: "inorganic" became "in organic". A spacing fix was always accepted because it keeps every letter, but splitting a real word changes its meaning. A real word is now split only when the corpus pair is at least 3× as common as the word (`anew` → `a new`: 8,108 against 14); otherwise never (`inorganic`, `carat`). Run-together non-words (`onyour`) are still split.
- **D38 (4.4.a, 4.5.c).** After the rules, a lower-case non-word that the model tried to change but whose fix was refused (often because the model rearranged the phrase: `would've hve been amaybe` → `would've maybe been`) gets the dictionary word that best fits the slip and the next word (`hve` → `have`, from "have been"). Never a word the model left alone (`helpdesk`), never a name or the word being typed, only one edit or two likely slips, and only a clear winner (3×); the typed word competes, so slang the UK word list knows and that fits ("gonna be") stays. A first version without these limits lost fixes and corrupted re-spaced words (`remem ber` → `rememher`); both are now tests.
- **D39 (4.4.b, 4.6.a; replaces D8's "never cross a line break").** User report (Intercom): a reply typed as several paragraphs was hardly corrected. (1) When the AI was triggered right after Enter, its context was the new, empty paragraph, so a paragraph finished with Enter never reached the AI. The context is now the paragraph that has just ended. (2) A fix may reach back over up to eight line breaks typed in this session (`MaxLineBreaksCrossed`; two was measured first and still dropped 11 fixes of a three-paragraph reply typed straight through): every editor tested moves over a paragraph break in one Left, the field is checked against the typed text before writing and verified after. Fast typists start the next paragraph before the fix arrives.
- **D40 (7.2, 7.3 extended at the user's request, 8.6).** The prediction history also keeps counts of the user's own short word sequences: two and three words within one sentence, with a sentence-start marker, from the same fields word counts come from (never password fields, excluded apps, elevated windows or while paused). Next-word prediction blends them with the corpus, weighted by how often the user has typed that context (once is already half the say), and completion boosts them ("how are you do" → "doing"). Never whole sentences, numbers or emails; capped at 60,000 phrases. 7.3 said "word counts only, never as sentences"; this keeps "never sentences" and adds pairs and triples. Also fixed: a word finished by punctuation and then a space was learnt twice.
- **D41 (4.6.c, 4.6.d).** Three findings from real use in Intercom and Teams. (1) 4.6.d says stop correcting a desynced field "for the rest of the session"; it was blocked for the life of the app, so one desync silenced every later reply. Now until the next session break. A write that was never sent (focus had moved) is a dropped write, not a desync. (2) The write deadline was 6 s, so the AI's fixes for a long reply typed without a 150 ms gap expired; it is now 60 s, and staleness is still caught by the checks just before writing and the verify after. (3) Verify polls for about a second (was 0.4 s) and only needs the text after the caret to still be there, since Edge can show its own suggestion right after the caret. A failed verify writes one line to `diagnostics.log`: app, kind of mismatch, unusual character codes, never text (8.6).
- **D42 (4.6.c, 4.6.d, 10.6, 10.7).** The root cause of "it works if I type slowly, not when I just type" (user reports in Notepad, Teams, Intercom): the app tracked the field by its own copy of the keys typed, and any difference between that copy and what the field reports ended the session silently. Real editors differ all the time: Edge reports a blank line as one line break (diagnostics: `lengthDelta=-2`), browser editors store double spaces as non-breaking, Notepad and Office autocorrect as you type (`lengthDelta=+7`), Edge shows its own suggestion after the caret, reads lag the last keys. Now: (1) typed text and field text are compared with runs of line breaks counted once (`TextNorm.Comparable`); (2) a mismatch before writing re-reads the field and carries on from its current paragraph (`TypingSession.Resync`) instead of ending the session; (3) a failed check after writing does the same, and only three in a minute leave the field alone for the session (4.6.d); (4) the check after writing allows typing, Enter included, after the fix. Caret steps over line breaks still count the Enter presses actually typed, so a blank line reported as one break can't shift a fix. The simulator models each of these behaviours (`SimulatedEditor.ReportsBlankLinesOnce`, `ReportsDoubleSpaceAsNbsp`, `GhostAfterCaret`, `LagChance`, host autocorrect) and the eval can run with all of them on (`--realistic`); each has an engine test that fails without the fix.
- **D43 (4.2 relaxed at the user's request, 14.4).** "You should be seeing everything": before each AI pass, the typed buffer is extended back to the start of the field's current paragraph (`TypingSession.ExtendToParagraph`), so text from before a click, a paste or dictation in that paragraph is corrected too. Other paragraphs are left alone. "Cautious" turns it off (`FixWholeParagraph`). Also: a non-word whose first key was extra or swapped ("tpargaea" → "paragraphs") gets the D36 leniency.
- **D44 (4.4.a, 4.6.d).** Found with the realistic simulator (D42), each with a test that fails without the fix. (1) Edge's text prediction shows a suggestion after the caret that comes and goes between reads; the check after writing compared the text after the caret exactly, which caused 23 desyncs in 25 realistic paragraphs. It now only requires the after-caret text to be consistent (`TextNorm.AfterConsistent`): the text before the caret is what proves the fix landed. (2) The AI's context is taken from the typed buffer (already checked against the field and extended to the paragraph start), so edit positions are in typed coordinates; taken from the field, they were off by one per blank line an editor reports as one break. (3) Enter ends a line for the AI even without a full stop. Realistic stress set: 67.2% → 88.5% fixed, desyncs 52 → 0, 96.7% of obvious misspellings fixed; tuning set unchanged.
- **D45 (4.4, 4.6.c).** Two lines each finished with Enter, typed straight through: the second line's fixes were all dropped ("text-moved"). The first line's fixes were written while the second line's request was out, which moved the text under it. The AI trigger now moves an in-flight request's positions by the size of any of our fixes written before its context (`AiTrigger.NoteOwnEdit`). The write gate also records why it dropped a write (`LastDropReason`: text-moved, too-many-lines, desynced, changed-on-read, not-sent, expired), as a code, never text.
- **D46 (10.7.a, 11.3).** The CI screen tests (GitHub Actions, Windows Server, mock model; `.github/workflows/e2e.yml`) found that in CKEditor 5, the editor in Microsoft Teams, a fix landed in the wrong place ("their" -> "there" changed the end of "dog"). CKEditor moves its own cursor from the browser's selection events, which arrive after the backspaces that follow a burst of arrow keys. For a field whose UIA class name contains `ck-editor`, fixes are now deleted back to and retyped instead of reached with arrow keys, and a fix whose retype would include a line break is skipped: retyping it would press Enter, which sends the message in Teams. The CI workflow now runs on every push to main.
- **D47 (4.3.a, 4.6.c).** The CI screen tests showed an intermittent "tthe og": the instant fix went out the moment the word ended, the user's next key was already on its way but not yet seen by the hook, and the retype deleted it. An instant fix now waits until no key has arrived for 60 ms (`InstantQuietMs`), which still meets 4.3.a's 100 ms; if the user types on within 60 ms, it waits for the next 150 ms pause like any other write. The harness and the eval now tick every 25 ms between keys, as the app does. UIA font and class name are read once per field, not on every read.
- **D48 (4.5.a, 4.3.c).** Of the obvious misspellings left on the realistic stress set, the model's own reply had fixed every one; the rules refused them. Mostly words run together with a small word dropped inside ("aboutkitchen" → "about the kitchen", "surelast" → "sure the last"): a non-word split into words that include function words is accepted when the other words' letters match what was typed to within one edit (a word swap still can't hide in a split, D26). And a capital I closing a run-together word ("thinkI", "sI") is a missed space before "I", not camelCase code.
- **D49 (4.4.a, the user's idea).** "Everything typed in the last few minutes should be scanned for obvious misspellings." After a 1.5 s pause, with nothing else to do, the app looks back over the whole typed stretch (up to 4,000 characters, across paragraphs, until the user clicks elsewhere) for a finished sentence that still holds an obvious misspelling (not in the dictionary, the personal dictionary or the UK word list; lower case; not the sentence being typed) and sends that sentence, with the one before it, to the AI again. Each sentence at most once, at most 20 per stretch; "Cautious" turns it off (`RevisitAfterMs`). The eval's final pause is 8 s so the look-back can happen, as it would when the user stops typing.
- **D50 (4.4, 4.5.a).** The last obvious misspellings on the realistic stress set were words split into pieces ("ne arly", "the ir", "att end"). The sweep (D38) now joins a non-word with its neighbour(s) when the joined letters are a dictionary word; if several joins work, the commonest word wins. Same limits as the sweep: only where the model tried to change the text, never a word it already fixed, a capitalised piece or the word being typed, and two real words side by side are never merged. Realistic stress: obvious misspellings left 6 → 3, fixed 89.5% → 90.6%, desyncs 3 → 0; tuning 94.4% → 94.6%.
- **D51 (7.1, 7.2, 7.3).** Word prediction was never scored. `eval predict` simulates typing and Tab-accepting: on unseen messages only about 23% of shown suggestions were right (the user: "none of the words were correctly predicted"). Causes and changes: (1) a word already complete was "completed" ("before" → "beforehand", "Leeds" → "Leeds's"): the word as typed now competes, and a bare "'s" is never suggested; (2) thresholds tuned on the tuning set (`RunnerUpRatio` 1.5 → 2.5, `MinNextShare` 0.4 → 0.6); (3) the user's own phrases (D40) count for two thirds after the same two words when typed once, half after one word. Holdout: right 23% → 43.5% with no history (44% with a learnt history), suggestions shown 3,748 → 2,150, keystrokes saved 10–14%.
- **D52 (9.3.b, 5.6.b).** Settings for the two things that reach beyond what was just typed, both on by default: "Fix the whole paragraph" (D43) and "Look back when you pause" (D49), on the Clean-up page. "Cautious" still turns both off and greys the switches out. Also "Free the AI's memory after" 5, 15 (default), 30 or 60 minutes without typing, for anyone who wants the 4 GB back sooner. Settings files from before D52 load with both switches on. A new test builds the Clean-up page from its XAML with the app's resources: it caught a misspelt icon name that would have crashed the page, and a row a text replacement had silently left out (CRLF vs LF).
- **D53 (7.6).** The new CI check of the suggestion's size (it measures letter heights on screen) found the suggestion about 15% small in CKEditor 5 in Edge: 10 px capitals next to the field's 12 px. The overlay takes the font size from the caret height divided by the font's line spacing, which is right where the caret is a line tall (Notepad, Win32, WPF). - **D63 (9.5, 9.1, 9.4).** Layout checks as tests, not just pictures (`tests/GlobalAutocorrect.App.Tests/Layout`). Every settings page and first-run step is laid out at the window's default and smallest size, at 100% and 200%: 40 layouts, each built once, and five checks run on each. (1) The page's rows are inside a ScrollViewer that scrolls vertically, and mouse-wheel turns over the page title (tunnelling then bubbling, as the input system sends them) bring the lowest row fully into view. (2) No text or control is clipped by its own box or any container (WPF's layout clip), cut short with an ellipsis, or beyond the window's right edge; nothing visible has no width or height. (3) No two interactive controls overlap. (4) Every interactive control has an accessible name (AutomationProperties.Name or what its automation peer reads from its own text). (5) Tab reaches every enabled control, and within the page goes top to bottom, left to right along a row. **How:** the window's content is taken out of the (never shown) window and put in a hidden `HwndSource` (a pop-up window handle without WS_VISIBLE). WPF treats it as on screen, so Loaded runs, the NavigationView navigates and keyboard navigation can be asked; nothing is ever shown and focus is never moved, so the tests can run while the user types. WPF-UI's title bar throws without its window, so it is replaced by an empty strip of its measured height. The tab order comes from WPF's own `KeyboardNavigation` (the code behind the Tab key), called through reflection without moving focus; if a future WPF renames it the tests fail rather than pass. **Scale:** WPF lays out in DIPs and the windows' sizes and minimums are DIPs, which Windows scales with the display and enforces, so laying out at size/scale would test a window that can't exist (half its minimum). What a scale does change is the pixels per DIP (layout rounding and text, set with `VisualTreeHelper.SetRootDpi`) and how many DIPs the screen has: at 200% a 1920 x 1080 screen with a 48-pixel taskbar offers 960 x 516, so the window is capped at that, never below its minimum (settings 920 x 520, first run 640 x 516). Each check is shown to fail on a small layout broken on purpose and to pass the same layout done right (`LayoutCheckFixtureTests`: no ScrollViewer, a ScrollViewer inside another, text cut off by its column, an ellipsis, text past the window, a zero-width button, two controls in one cell, an unnamed TextBox and RadioButton, a control Tab skips, Tab going back up or right to left); a guard test checks the layouts show their fullest content (an update on offer, dictionary words, the Download button). **Found and fixed:** (a) the mouse wheel didn't scroll any settings page longer than the window (Clean-up and About at the default size; Apps and Dictionary at the smallest or at 200%): the NavigationView wraps each page in its own scroll viewer, so each page's ScrollViewer was given its full height, never scrolled, and still marked every wheel turn handled; the pages' own ScrollViewers are gone. (b) The first-run window had no ScrollViewer: step 1's last line was cut off at the smallest size, and any taller content would have pushed under the buttons; the step area now scrolls (the buttons stay put) and each step starts at its top. (c) WPF-UI's `CardControl` is a button: each settings card was a Tab stop with no name that did nothing; an implicit style in Components.xaml makes cards not focusable, so Tab goes straight to the switch, list or slider. (d) The three boldness radio buttons had no accessible name ("Cautious", "Standard", "Bold" now). Also each chip's remove button is named after its word or app ("Remove notepad"), not just "Remove". Before the fixes the checks reported 25 scrolling, 2 clipping and 52 name problems; overlap and tab order found none. **Not checked:** colour contrast and alignment (screenshots and the token contrast test), the open drop-downs of the ComboBoxes (pop-ups), Windows' separate "Text size" setting, and high-contrast themes.
